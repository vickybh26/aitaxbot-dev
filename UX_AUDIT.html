The one-paragraph version

This is a genuinely well-reasoned product. The code is unusually well-documented, several decisions are backed by real usage data, and the recent direction — navy over "AI purple", show the headline number before the sign-in gate — is the right instinct for a tax product. The problem is not judgement, it is layering. A design-token system was installed, then broken at the root by a one-line mapping bug, then worked around 296 times with bg-white. Three separate design specifications now exist and contradict each other. The result is a site that renders acceptably but where nobody can change a colour with confidence. Fix the token layer first — most of the visual inconsistency below is downstream of it.

P0 The shadcn token layer is broken at the root — every Card and outline Button renders wrong Design system · affects 88 Cards, 58 Buttons, 32 other usages ›

tailwind.config.ts maps the shadcn tokens straight to the CSS variables: primary: "var(--primary)". But in index.css those variables are declared as bare HSL triplets — --card: 0 0% 100%. The utility therefore emits background-color: 0 0% 100%, which is invalid CSS and does nothing.

The persian-blue scale in the same config gets this right (hsl(var(--persian-blue-50))), which is why that ramp works and nothing else does.

What actually renders
  • <Card> ships "rounded-lg border bg-card". bg-card is a no-op → transparent. border has no colour because border-border is also broken → the border falls back to currentColor, i.e. the inherited dark body text colour. Every one of the 88 cards draws a near-black hairline instead of a light grey one.
  • <Button variant="outline"> (51 uses) = bg-background + border-input — both dead. Transparent button, currentColor border.
  • secondary (6), destructive (1), ghost (5) likewise have no background.
  • focus-visible:ring-ring is dead on every shadcn component. Only the global :focus-visible rule in index.css is keeping keyboard focus visible at all.
  • Unpatched and in use: bg-background ×15, bg-muted ×9, bg-popover ×8, bg-secondary ×8, bg-destructive ×5, text-foreground ×10.

The 296 hand-written bg-white classes and the growing block of .text-*-foreground rescues in index.css are scar tissue from this single bug. The file's own comments already diagnose it correctly and label the proper fix "when there is time" — this audit's position is that it is the highest-leverage hour available.

Fix

Wrap every token in hsl() in the Tailwind config, matching what persian-blue already does, then delete the rescue block and the .bg-primary/.text-primary patches from index.css.

- background: "var(--background)",
- primary: { DEFAULT: "var(--primary)", foreground: "var(--primary-foreground)" },
+ background: "hsl(var(--background))",
+ primary: { DEFAULT: "hsl(var(--primary))", foreground: "hsl(var(--primary-foreground))" },
  // …same for card, popover, secondary, muted, accent, destructive, border, input, ring

Do it on a branch and walk the site once — some pages have been visually tuned around the broken behaviour, so a handful of bg-white overrides will need removing rather than keeping. Budget half a day, not an hour, for the sweep.

P0 The site makes three contradictory claims about whether it stores your data Content · trust-critical · homepage + every calculator ›

Users are handing over salary figures and PAN-adjacent data. The copy tells them three different things about what happens to it:

  • Homepage trust ribbon — "Runs in browser — data never stored"
  • Tax calculator badge — "No data stored"
  • Result gate — "Signing in saves your latest result to your dashboard — you can clear it any time"

The third is the accurate one. The calculator POSTs to the API, the Dashboard reads saved calculations back, and the AIS tool uploads Form 16 / 26AS PDFs for server-side parsing. The first two are false as written.

This is not pedantry. In a tax product, a visible contradiction about data handling is the cheapest possible way to lose a cautious user — and the cautious user is exactly the one who reads trust ribbons. It also sits awkwardly against DPDP disclosure expectations.

Files
client/src/pages/Landing.tsx:251–262client/src/components/calculators/TaxCalculator.tsx:987–996client/src/components/ResultAuthGate.tsx:101–104
Fix

Make one true claim and repeat it verbatim everywhere: "Calculations run in your browser. Nothing is saved unless you sign in." That is both accurate and still a strong reassurance — arguably stronger, because it is specific.

P0 Printing is disabled site-wide — users cannot print or PDF a tax computation Accessibility · Flow · every page including Terms & Privacy ›

index.css ends print output entirely:

@media print {
  body { display: none !important; }   /* line 141 */

The stated intent is to funnel users to the Download button. But the rule is total: Ctrl+P and "Save as PDF" produce a blank page on the homepage, the blog, the Privacy Policy and the Terms of Service. Printing a tax computation for your own records or your CA is a completely ordinary thing an Indian taxpayer does in filing season, and refusing it silently — the user gets no message, just a blank sheet — reads as a bug, not a policy.

It also blocks some print-to-reader and offline-archive workflows used by assistive tooling.

The counter-case, stated fairly

There is a real argument here: a browser-printed calculator page would be an ugly, half-broken artefact with navigation and ads in it, and a user forwarding that to their CA reflects badly on the product. The generated PDF is genuinely better. The disagreement is only about method — that is an argument for a good print stylesheet, not for a blackout, and it does not justify blanking the Terms of Service.

Fix

Replace the blackout with a real print stylesheet: hide header, footer, tab bar, FAB, cookie banner and ad slots; keep the result card, the breakdown table and a one-line "Generated by aitaxbot.co.in · not a filed return" footer. Roughly 20 lines. Keep the Download PDF button as the promoted path.

P1 The Hindi toggle is a promise the product doesn't keep Content · Flow · 62 keys, 18 call sites, 3 files ›

The language switcher is given prime real estate — desktop header and mobile header, visible before anything else. Behind it:

  • en.ts / hi.ts: 62 keys each
  • useTranslation() imported in exactly 3 files: Header, Landing, i18n.tsx
  • 18 t() call sites across ~18,850 lines of UI

Tapping हिंदी translates the nav labels and the hero headline. Every calculator label, every field, every result, every error message, every FAQ, the entire blog and all 38 pages stay in English. A Hindi-preferring user is arguably worse off than with no toggle: they have been told the product speaks their language, made a choice, and been handed the same English form with a translated menu bar on top.

The translation keys also reference features that no longer exist — footer.mutualFunds, footer.stockQuotes, footer.ipoAnalyzer, footer.marketNews — pointing at the archived _backup/market module.

Fix — pick one
  • Commit. Translate the Income Tax Calculator end-to-end first (391 of 464 measured page views land there). One fully bilingual high-traffic page beats 38 half-done ones.
  • Or scope it honestly. Keep the toggle, but only render it on pages that are actually translated, and label it "हिंदी (beta)".
  • Or remove it until there is capacity. An absent feature costs less trust than a hollow one.

These are not variations, they are three different products. P1 Hand-rolled modals have no dialog semantics, focus trap or Escape key Accessibility · 5 modals · Radix Dialog already installed ›

Five overlays are built as plain fixed inset-0 divs rather than using the Radix Dialog that is already in components/ui/:

ProfileCompletionModal.tsx:75FindCA.tsx:525 TaxDownloadModal.tsx:126ui/modal.tsx:28AdminUsers.tsx:273

None of them has role="dialog", aria-modal="true", a labelled title, a focus trap, an Escape handler, background scroll-lock, or focus restoration on close. A screen-reader user is not told a dialog opened; a keyboard user tabs straight out of it into the page behind; Escape does nothing.

P2 The first mobile tab is a login wall for the 99% who are first-time visitors Flow · Mobile · MobileTabBar.tsx:38 ›

Tab 1 is Dashboard, and /dashboard is a ProtectedRoute. An anonymous visitor's most likely first tap on the new navigation redirects them to /login?returnUrl=/dashboard — where the payoff is an empty dashboard.

Two further wrinkles:

  • matches: ["/"] makes the Dashboard tab render as active on the homepage. The user is told they are on Dashboard while looking at the marketing page.
  • The component's own docstring notes that 99% of sessions are first-time visitors — which is an argument against giving them a signed-in-only first tab.
The counter-case, stated fairly

The docstring's reasoning is sound as far as it goes: returning users' saved results live on the dashboard, and there is no other "home screen". The flaw is not the destination, it's the position and the unconditional label.

Fix

Make tab 1 conditional: Home → / when signed out, Dashboard → /dashboard when signed in. Drop matches:["/"] so the active state is honest. Optionally promote Calculators to position 1 for anonymous users, since that is where 84% of measured traffic already lands.

P2 The tax calculator uses tabs for a linear task, creating two empty states Flow · TaxCalculator.tsx:985–1011 (1,953 lines) ›

The flagship calculator is a three-tab control: Calculator / Results / Tax Breakdown. Tabs imply peer views you can browse in any order. This is a strict sequence: you cannot have results before you calculate.

  • Tabs 2 and 3 are clickable from first paint and lead to empty panels.
  • Calculating fires setActiveTab('results') — the view teleports, which on mobile means the user's scroll position and mental place both reset.
  • Results and Breakdown are conceptually one answer split across two tabs, so comparing the number to its derivation requires a click.
Fix

Either (a) render the result below the form on the same page and smooth-scroll to it — the pattern the SIP/HRA calculators and the homepage SavingsCard already use successfully — or (b) keep tabs but disable 2 and 3 until result !== null and merge Breakdown into Results as a collapsible section. Option (a) is closer to how the rest of the site already behaves.

P2 Dark mode is half-wired: 18 dark: utilities, zero dark tokens, no toggle Design system ›

tailwind.config.ts declares darkMode: ["class"]. index.css contains zero .dark or [data-theme] blocks, and no UI ever sets the class. Meanwhile 18 dark: utilities are scattered through components — e.g. CookieConsent styles a dark:bg-gray-900/95 panel that can never render.

Harmless today, but it is a trap: the next developer sees dark: classes, assumes dark mode is supported, and builds a page for a mode that does not exist.

Fix

Strip the 18 dark: utilities and drop darkMode from the config, or commit to it properly by adding a .dark token block. Given the trust-through-restraint positioning and a white-first palette, removing is the cheaper honest answer.

P2 No skip link, and 18 inputs rely on placeholder text alone Accessibility · WCAG 2.4.1, 3.3.2 ›
  • No skip-to-content link. On a calculator page a keyboard user tabs through the logo, six nav links, a dropdown, a CTA, a language toggle and a login link before reaching the first form field — on every page load.
  • 18 inputs have a placeholder but no id/htmlFor pair. Placeholders vanish on focus and are not reliably announced. Overall the ratio is decent (104 htmlFor against 213 inputs, many of which are Radix-wrapped), but the gap is concentrated in the contact and CA-registration forms.

Add <a href="#main" class="sr-only focus:not-sr-only …">Skip to content</a> as the first child of Layout, and id="main" on the existing <main> (2 lines). P2 Dropdowns are mouse-only: no aria-expanded, no Escape, no keyboard close Navigation · Accessibility · Header.tsx:29–37 ›

The header's "More" and user-avatar menus are hand-built. They close via a mousedown listener on document only. Consequences:

  • No aria-expanded / aria-haspopup — a screen reader announces "More, button" with no indication it opens a menu or that it is currently open.
  • Escape does not close them.
  • Tabbing away leaves the panel open and floating over the page.
  • Touch devices fire mousedown inconsistently, so on some phones an outside tap won't dismiss.

The mobile drawer has the same issue, and additionally stays open on browser back-navigation because it only closes through explicit onClick handlers.

Fix

Swap both for the Radix DropdownMenu already sitting in components/ui/dropdown-menu.tsx — it handles roving focus, Escape, typeahead and ARIA. For the mobile drawer, close it on location change with a useEffect rather than per-link handlers.

P3 Ad slots reserve no space — enabling real slots will shift results on click Flow · AdBanner.tsx ›

All three slot IDs are placeholders (1234567890 etc.), so AdBanner currently returns null and nothing renders. The moment real IDs land, a ResponsiveAd and a RectangleAd will inflate directly beneath the result on every calculator page, pushing content down — classic cumulative layout shift, and worst on the exact page where the user is reading a number.

Fix

Reserve the space now: wrap each slot in a container with an explicit min-height matching the ad format, so enabling ads is a no-shift change. Also consider moving the ad block below the FAQ rather than immediately under the result — an ad adjacent to a tax figure hurts the "CA-reviewed" positioning.

P3 The WhatsApp button pulses forever next to the user's tax result Mobile · WhatsAppButton.tsx:88 ›

An animate-ping ring runs indefinitely, and an unsolicited tooltip appears at 5s and leaves at 12s. On a results page the brightest moving thing on screen is a chat button, not the number the user came for. Attention is a fixed budget.

Credit where due: the global prefers-reduced-motion block in index.css does neutralise the animation for users who ask for that — good, and better than most sites manage.

Fix

Limit the pulse to ~3 iterations on first load, then stop. Suppress the tooltip on calculator result views. Persist dismissal to localStorage rather than component state, so it doesn't reappear on every page navigation.

P3 The 404 page is built entirely off-system Design system · not-found.tsx ›

Two of its four tiles are borderless border-2 border-gray-300 blocks with no background, so the grid reads as two buttons and two outlines rather than four peers.

Minor, but 404s are disproportionately seen by people arriving from stale search results — i.e. first impressions.

Fix

Convert to slate, make one action primary (Home, navy) and the other three consistent outlined tiles. Add a search or a link to the Calculators hub.

What's working — keep it

Genuine strengths worth protecting through the refactor

  • The colour rationale is right. Retiring the blue→purple AI gradient for institutional navy, and reserving green strictly for money gained, is exactly the correct call for a tax product. The reasoning is written down in index.css, in full, with the evidence.
  • Decisions are documented and evidence-backed. MobileTabBar cites 391/464 page views; ResultAuthGate cites 123 signups against 22 completed calculations. Design arguments grounded in numbers are rarer than they should be.
  • The headline-before-gate change is correct. Showing the answer and charging sign-in for the breakdown is the right trade, and directly addresses both the drop-off and the AdSense "low value content" finding.
  • Accessibility fundamentals are present where they matter. A global :focus-visible ring that is explicitly never removed, a full prefers-reduced-motion block, aria-current on the tab bar, 56px touch targets, and aria-labels on the icon-only controls that matter most.
  • tabular-nums on money. A small, expert detail — rupee columns stay aligned and digits don't jitter as live values update.
  • Sensible performance architecture. Landing and Login eager, all 36 other routes lazy — a ~600–800 KiB saving on first paint, on the page that matters most.
  • The footer is the most consistent surface on the site. One palette, correct contrast, clear column hierarchy, and a well-judged supply-side "For CAs" column. Use it as the reference when normalising everything else.
  • Calculator pages share real components. All nine wrap components/calculators/* with a common CalcPageHeader — no copy-paste duplication. The structure is sound; only the tokens under it are broken.
